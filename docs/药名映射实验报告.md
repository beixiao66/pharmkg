## 2. 方法

**翻译**：百炼 `qwen-plus`，每批 25 个药名，强制 JSON 输出。
**提示词自检 8/8 通过**（`Warfarin→华法林`、`Metformin→二甲双胍`、
`Acetylsalicylic acid→乙酰水杨酸` …），说明译名质量可用。

**匹配**：基线决策 #23 的五级字符串匹配，从高置信到低置信依次尝试：

| 级别 | 方法 | 计入覆盖率 |
|---|---|---|
| ① 原样精确 | 译名与词表完全相同 | ✅ 确定命中 |
| ② 别名表 | 命中 OpenCMKG 自带 `SameAs` 里的别名 | ✅ |
| ③ 归一化精确 | 去括号、去剂型后缀后相同 | ✅ |
| ④ 去盐归一化 | 再去掉盐/酯形式（盐酸、钠、钾…）后相同 | ✅ |
| ⑤ 拼音相同 | 同音不同字 | ⚠️ **待确认** |
| ⑥ 编辑距离 | `rapidfuzz >= 85` | ⚠️ **待确认** |

**不用向量**。药名匹配是字符串与别名问题，不是语义问题。

## 4. 为什么 70% 未命中：不是方法问题

对 1,355 条未命中做了两项诊断：

**① 这些译名出现在别的 Label 下吗？**

| 情况 | 条数 |
|---|---:|
| **任何类型里都没有** | **1,352（99.8%）** |
| 出现在 `symptom` | 2 |
| 无译文 | 1 |

**② 它们与词表"最相似"的程度分布？**

| 相似度 | 条数 | 含义 |
|---|---:|---|
| 80–90 | 40 | 差一点 |
| 70–80 | 97 | |
| 60–70 | 193 | |
| **50–60** | **571** | 只是碰巧共用了几个汉字 |
| < 50 | 453 | 完全不沾边 |

**结论**：译名是对的（`Abacavir→阿巴卡韦`、`Abiraterone→阿比特龙`），
**OpenCMKG 就是没有这些药**。它的 4,289 个药偏"中国上市的大众品种"，
而 DDInter 覆盖全球专业药——高频 Major 药里没命中的是
`Siponimod`、`Ozanimod`、`Fingolimod`、`Osimertinib`、`Tofacitinib`、
`Infliximab`、`Iohexol`（造影剂）这类肿瘤/免疫/专科药。

> **基线 §13.5 的判读表需要修正**：它把「低全量 + 低 Major」判为
> "存在系统性问题 → 停下，重做映射方案"。实测表明**方法没问题，
> 是词表的覆盖边界**——这两者要采取的行动完全不同。

## 5. 三个与基线假设不符的发现

### 5.1 编辑距离在医药场景不可靠（决策 #23 需要收紧）

53 条命中里约 20 条是错的（38%）。原因很直白：**中文药名常常只差一两个字，
但那两个字决定它是不是同一种药**——`红霉素`/`柔红霉素`、`氯噻嗪`/`氢氯噻嗪`、
`环磷酰胺`/`异环磷酰胺`、`凝血因子VIII`/`XIII`。

**处置**：⑤⑥ 级标为「**待确认**」，只作为候选推给用户澄清（对应 §6.5 的
"澄清反问"），**不计入覆盖率**。按项目「不臆造」原则，宁可不匹配，
也不能给用户一个错的药。

### 5.2 拼音匹配对"中→中"几乎没用

只命中 1 条（`林丹 → 林旦乳膏`，0.1%）。因为这里的匹配双方都是**规范中文药名**
（LLM 译名 vs 词表），不存在用户手输的打字错误。

**拼音真正的用武之地在 L5 的查询期**——用户输入"阿莫西灵"这类错别字时才有价值。
所以在 §6.5 的五级设计里，拼音应该服务**用户输入 → 词表**这一侧，
而不是本实验的 **LLM 译名 → 词表**这一侧。

### 5.3 别名表（SameAs）对药名贡献为 0

`entities_dict` 里 **7 类共 60,696 个实体，但 `SameAs` 里两端都是 drug 的只有 8 对**。
SameAs 绝大多数是**症状**同义词（`下肢疼痛 ↔ 腿疼`）。

基线 §6.5 把"OpenCMKG 自带 17,977 条 SameAs"列为药名别名表的主要来源——
**这一条要改**。药名别名表得另想来源（LLM 生成商品名、或外部药典）。

## 6. 对 L2 的影响：一个需要拍板的策略选择

**关键数字：只有 6.0% 的 Major 药对两端都能映射到 OpenCMKG 已有药物。**

| 范围 | 药对总数 | 两端都能映射 | 占比 |
|---|---:|---:|---:|
| 全部 | 160,235 | 22,472 | 14.0% |
| Major + Moderate | 123,589 | 10,594 | 8.6% |
| **只算 Major** | **26,914** | **1,608** | **6.0%** |

（反向也低：OpenCMKG 的 3,558 个主成分里只有 **11.6%** 有 DDI 数据。）

### 两个选项

**方案 A：只导入能映射上的边**
- 图上干净，每条 DDI 边都挂在有适应症信息的药上
- 代价：Major 药对只剩 6%，**药箱放两个药几乎必然回答"图谱中无相关记录"**——功能形同虚设

**方案 B：映射上的挂已有节点；映射不上的新建 Drug 节点（推荐）**
- 用 LLM 译名作节点名，标 `source=ddinter`
- **DDI 检查立刻变成 100% 可用**：1,939 个药、160,235 对相互作用全部入图
- 代价：这些新节点**只有 DDI 数据，没有适应症/推荐关系**——问"阿巴卡韦治什么"答不出来
- 与基线既有约定一致：§13.7 的接缝处理就是"对不上的新建节点并标来源"，
  §13.8 要求"每条链路写入的节点带 `source` 属性"

> **我的建议是方案 B。** 理由：药箱的核心价值是**相互作用检查**，
> 而那只需要"这个药存在 + 有 DDI 边"，不需要它的适应症。
> 用方案 A 会把整条 L6 做成摆设。
>
> 但这是个**要写进论文的取舍**：方案 B 意味着图谱里会有一批"只有相互作用、
> 没有适应症"的节点，需要在"局限"一节说明。

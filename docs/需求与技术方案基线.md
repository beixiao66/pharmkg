## 1. 项目目标与验收标准

**课题**：基于 AI 与知识图谱的医药查询与智能用药系统

**"做完了"的定义**（三条同时满足）：

1. 一个可本地一键启动的 Web 系统，用户能：注册登录 → 自然语言多轮提问医药问题 → 得到**可追溯到图谱证据**的回答 → 添加常服药物到"我的药箱" → 一键检查相互作用风险。
2. 一张自建/融合的中文医药知识图谱，落库 Neo4j，可被 Cypher 查询，含疾病、药物、症状、相互作用、禁忌等关系。
3. 一组**冻结的测试集 + 量化指标**：单轮问答准确率、多轮指代消解成功率、抽取准确率、消融对比（纯 LLM vs 图谱增强）。

### 1.1 明确要做的能力

| 能力 | 说明 |
|---|---|
| ✅ **单轮问答** | 一问一答，系统主入口 |
| ✅ **多轮对话** | 带会话上下文，支持指代追问（"那**它**有什么副作用？"） |
| ✅ **会话持久化** | 会话列表 + 历史消息可回看，刷新/重登不丢 |
| ✅ **用药安全校验** | 基于"我的药箱"的相互作用与特殊人群检查 |
| ✅ **按疾病推荐候选药物** | 只到**药物清单**粒度 + 推荐依据 |
| ✅ **图谱可视化** | 定位为回答的"证据路径展示层"，非独立功能 |
| ✅ **数据看板（只读）** | 图谱规模统计、数据来源与许可说明、药名映射覆盖率与抽取质量报告；**只读，不做增删改** |

### 1.2 明确不做（范围冻结）

- ❌ 不训练/微调实体识别或抽取模型（用 LLM + 现成数据）
- ❌ 不输出具体剂量/疗程的用药方案（只到**药物清单**粒度）
- ❌ 不做联合用药组合推荐、不做开放域闲聊
- ❌ 不爬取商业医药数据库
- ❌ 不做云端部署（本地 Docker Compose 为准）

## 2. 关键技术决策汇总

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 核心命题 | 图谱构建 + 智能问答 + 用药安全校验 | 三块互相支撑，工作量均衡 |
| 2 | "AI"落点 | LLM + RAG（图谱作检索源），不训模型 | 周期内最稳，无需 GPU |
| 3 | 主骨架图谱 | **OpenCMKG** ✅ | 疾病 14726 / 药物 4289 / 三元组 354755（**四项全数实测吻合**），含 `disease_recommand_drug` 60621 条 |
| 4 | DDI 数据 | **DDInter** ✅ | CSV 实测 **1939 药 / 222383 条记录 / 160235 去重药对**，含严重程度分级（**无机制与处理建议**，见 §5 注） |
| 5 | 禁忌/特殊人群 | **LLM 从 NMPA 说明书抽取自建** | 无任何公开中文结构化数据集覆盖，必须自建 |
| 6 | 图谱检索方式 | **Text2Cypher** | 可解释性最强，每条回答可追溯 |
| 7 | 问答形态 | 自然语言问答为主 + 图谱可视化辅助 | 可视化定位为"证据路径展示层"，非独立功能 |
| **7a** | **对话轮次** | **支持多轮对话**——用**查询改写前置层**实现，不让 LLM 直接维护 Cypher 上下文 | 演示需连续追问；改写层使单轮链路零改动 |
| **7b** | **会话存储** | 持久化到数据库，含会话列表与历史回看 | 刷新/重登不丢，可演示多会话切换 |
| 8 | 用药推荐粒度 | 只到**药物清单** + 推荐依据 | 剂量数据不可得，摘掉最不可控的依赖 |
| 9 | 中英药名对齐 | LLM 批量翻译 + 人工抽检评估 | 同时产出论文"实体对齐"章节 |
| 10 | LLM 服务 | DeepSeek / 阿里云百炼（OpenAI 兼容） | 统一 provider 抽象层，可换模型 |
| 11 | 技术栈 | FastAPI + Neo4j(Docker) + Vue3 | 资料最多、答辩最认、环境可复现 |
| 12 | 交付形态 | 本地 Docker Compose | 不依赖答辩教室网络 |
| 13 | 用户体系 | 登录 + 我的药箱 + 相互作用检查 | 把孤立的安全校验变成自然用户场景 |
| 14 | 评测方案 | 100–200 条测试集（含多轮子集）+ 消融对比 | 一个测试集支撑两章 |
| 15 | 额外时间投向 | 图谱规模、评测深度、论文质量 | 不新增**业务**模块，避免样样半成品 |
| 16 | 前端形态 | **一套用户端 + 一个只读数据看板页**；不做管理端、不做数据上传 | 图谱数据全部由离线管线写入（L1/L2/L4），从不经过前端；数据看板只读因而不引入审核责任 |
| 17 | 关系数据库 | **PostgreSQL 16**（实测 16.15） | 消息表要存证据子图 JSON，JSONB 可索引可查询；后续若需向量检索可直接加 pgvector，不必引入中间件 |
| 18 | Python 版本 | **3.13**（本机 3.13.15） | 3.9 已停止维护，且 3.9.0 自带 OpenSSL 过旧，会导致 pip 连国内镜像 TLS 握手失败 |
| **19** | **DDI 信息深度** | **方案 A：`INTERACTS_WITH` 只建 `level` + `source`**，不抓 DDInter 详情页 | 实测 CSV 只有 5 列，机制/处置建议不在其中。省下的时间投给技术风险最高的 L5（问答链路）；机制与处置建议写入论文「局限与展望」 |
| **20** | **数据获取方式** | **脚本化下载**（`scripts/download_data.py`），原始数据不入库 | 体积大（33.5 MB）+ DDInter 有 SA 再分发限制；脚本 + 来源 URL + SHA-256 可完整重建 |

## 5. 图谱 Schema 设计（草案）

> ⚠️ **本节已按 `docs/数据源实测报告.md` 修正**（2026-09-24）。
> 原草案是下载数据之前的推测，实测后有多处不符：`Check` 无词表、关系漏了 5 类、
> `INTERACTS_WITH` 的属性只有 `level` 拿得到。

**节点**

| Label | 关键属性 | 来源 | 实测规模 |
|---|---|---|---|
| `Drug` | `id, name_cn, name_en, aliases[], atc_code` | OpenCMKG + DDInter | 4,289（中文）/ 1,939（英文 DDI） |
| `Disease` | `id, name` | OpenCMKG | 14,726 |
| `Symptom` | `id, name` | OpenCMKG | 12,578 |
| `Population` | `id, name`（孕妇/哺乳期/儿童/老年/肝功能不全/肾功能不全） | 自定义枚举 | 6 |
| `Food` | `id, name` | OpenCMKG | 4,846 |
| `Department` | `id, name` | OpenCMKG | 54 |
| `Producer` | `id, name` | OpenCMKG | 16,772 |
| `Treatment` | `id, name` | OpenCMKG | 598 |
| `Check` | `id, name` | OpenCMKG `disease_need_check` | 3,351（**无词表，现场收集**） |

> 这 3,351 个检查项只能从三元组尾实体现场去重收集，且没有别名可用。

**新增关系（多源融合 / 抽取产物）**

| 关系 | 方向 | 属性 | 来源 |
|---|---|---|---|
| `INTERACTS_WITH` | Drug ↔ Drug | `level(Major/Moderate/Minor/Unknown), source` | DDInter |
| `CONTRAINDICATED_FOR` | Drug → Disease/Population | `source, evidence` | 说明书抽取 |
| `CAUTION_FOR` | Drug → Population | `level, source, evidence` | 说明书抽取 |

> ⚠️ **`INTERACTS_WITH` 只有 `level` 拿得到**。原草案里的 `mechanism` / `description` /
> `management` / `alternative_drug` / `citation` **不在 DDInter 的 CSV 里**，
> 只存在于网站药物详情页。
>
> **【已决策 2026-09-24 · 方案 A】** `INTERACTS_WITH` **只建 `level` 与 `source` 两个属性**，
> 不抓详情页。系统对相互作用的回答止于「存在相互作用 + 严重程度」。
> 机制与处置建议写入论文「局限与展望」，不作为交付内容。
> 理由：把省下的时间投给 **L5（问答链路）**——实体链接与 Text2Cypher 是技术风险最高的部分。
> 依据见 [`docs/数据源实测报告.md`](数据源实测报告.md) §3.1、§6。
>
> 若后期时间富余，方案 B（抓详情页补机制/处置建议）仍可作为扩展，但**不在当前承诺范围内**。

> ⚠️ **`SAME_AS` 是 OpenCMKG 自带的**，不是我们的对齐产物。我方的实体对齐结果应使用
> 不同标签（如 `ALIGNED_TO`）或加 `source` 属性区分，避免把上游数据和自己的成果混为一谈。

> **主键策略**：`Drug` 以**中文通用名归一化后**为主键，剂型与盐形式入 `aliases`。
> 实测 78.1% 的中文药名带剂型后缀，且同一主成分最多分裂成 7 个实体
> （如利巴韦林 → 胶囊/颗粒/滴眼液/泡腾颗粒…），**不归一化会严重低估映射覆盖率**。

## 6. 核心流程设计

### 6.1 问答链路（多轮 + Text2Cypher）

```
用户提问（携带 conversation_id）
  → ⓪ 查询改写【多轮关键步骤】
        输入：最近 N 轮对话 + 当前问题
        输出：一个自包含的完整问题
        规则：若当前问题已含药物实体 → 跳过改写，直接进入下一步
  → ① 意图识别：相互作用 / 适应症 / 疾病用药 / 禁忌 / 药品信息 / 其他
  → ② 实体链接：别名词典精确匹配 → 向量相似度兜底 → 置信度阈值判定
        （低于阈值 → 触发澄清反问，绝不硬猜）
  → ③ Text2Cypher：注入 schema + few-shot 示例 → 生成 Cypher
        → 白名单校验（仅允许 MATCH/RETURN，禁止写操作）→ 超时 + 条数上限
  → ④ 执行查询，取回结构化事实
  → ⑤ 生成回答：仅基于查询结果，禁止外推；无结果时明确回答"图谱中无相关记录"
  → ⑥ 落库：持久化 {原问题, 改写后问题, Cypher, 证据, 回答} 到 message 表
  → ⑦ 返回：回答 + Cypher + 证据子图 JSON + 免责声明
```

> **为什么不让 LLM 直接基于历史生成 Cypher**：历史 Cypher 会污染当前生成，导致错误率上升且难以定位是哪一轮引入的问题。查询改写把"多轮"折叠成"单轮"，使 ③④⑤ 三步完全复用单轮逻辑。

### 6.2 多轮对话与会话管理

**数据表设计**

```sql
conversation(id, user_id, title, created_at, updated_at)
message(id, conversation_id, role, content,
        rewritten_query,        -- 改写后的自包含问题（调试与评测的关键证据）
        cypher,                 -- 实际执行的 Cypher
        evidence_json,          -- 证据子图
        created_at)
```

**实现要点**

- `rewritten_query` **必须落库**——它既是调试依据，也是评测多轮指代消解是否成功的直接证据。
- 会话标题由首条问题自动生成（取前 20 字即可，不必额外调 LLM）。
- 上下文窗口用**最近 N 轮**（建议 N=3）而非全量历史，控制 token 成本。
- 改写失败的降级策略：若改写超时或返回空 → 直接用原问题走单轮链路，不阻断用户。

### 6.3 用药安全校验（"我的药箱"）

```
用户药箱 [药A, 药B, 药C]
  → 检查两两组合：MATCH (a)-[r:INTERACTS_WITH]-(b)
  → 按 level 排序（Major 优先），输出机制 + 处理建议 + 替代药
  → 叠加特殊人群检查（若用户填了人群标签）：CONTRAINDICATED_FOR / CAUTION_FOR
  → 前端以"风险卡片 + 图谱子图"呈现，全部附免责声明
```

### 6.4 说明书抽取管线（离线）

```
① 选样：从 DDInter 中统计出现在 Major 级相互作用里频次最高的 N 种药（数据驱动选样）
② 采集：NMPA 官网逐条说明书，限速、限量、记录 URL 与采集日期
③ 抽取：LLM + 强制 JSON 输出，槽位 = {禁忌, 特殊人群慎用, 注意事项}
④ 质检：同一文本两次抽取比对 → 不一致条目送人工；随机抽 100 条人工核对算准确率
⑤ 入库：对齐到已有 Drug 节点，写入 CONTRAINDICATED_FOR / CAUTION_FOR
```

## 7. 评测方案

| 评测项 | 数据 | 指标 |
|---|---|---|
| 实体抽取准确率 | 随机抽 100 条说明书抽取结果人工核对 | Precision / Recall / F1，错误分类（漏抽/错配/幻觉） |
| **实体对齐准确率** | **OpenCMKG 自带的 `manual_annotation.csv`（852 条人工标注）** | **准确率 / P / R / F1**——这是他人已标注的金标准，比自己临时标注更可信 |
| 药名映射质量 | 抽 200 个 DDInter 药名 | 映射准确率 + **覆盖率**（1939 个英文药名能对上多少中文药） |
| 单轮问答效果 | 自建 100–200 条测试问答集 | 答案准确率、实体链接命中率、Cypher 执行成功率 |
| **多轮指代消解** | **测试集中独立的多轮子集（30–50 组连续追问）** | **改写成功率、指代消解准确率、末轮回答正确率** |
| 消融对比 | 同上测试集 | 纯 LLM vs 图谱增强 LLM；单轮 vs 多轮 |
| 图谱规模 | Neo4j 统计 | 节点数、边数、覆盖药品种类数 |

> **关键纪律**：测试集必须**先于系统完成前构建并冻结**，否则会不自觉地按系统已有能力出题（自己出题自己考，必被追问）。
> **多轮子集设计要点**：必须包含三种指代类型——代词指代（"它/这个药"）、省略指代（"那布洛芬呢"）、话题延续（"还有别的吗"），并标注标准改写结果。
> **可引用基线**：CH-DDI 论文报告中文 DDI 关系抽取 F1 为 **78.43%**，可作为你抽取效果的参照物。
> **意外收获**：OpenCMKG 除了图谱还附带 `manual_annotation.csv`（852 条实体对齐人工标注，
> 560 正 / 291 负）和 17,977 条 `SameAs` 关系，可直接用于实体链接的评测与监督，
> 不必从零构造标注集。详见 [`docs/数据源实测报告.md`](数据源实测报告.md) §2.5–2.6。

## 13. 链路清单与验收标准

> 本节是第 6 节「核心流程设计」的细化，也是**开发的推进单位与验收依据**。开发按链路走：一条一条打通，一条一条验收。

### 13.1 什么是「链路」

一条**从输入走到输出的完整通路**：中间每一步依赖上一步的产出，最后必然得到一个确定的输出。

判断标准：**中间任何一环断了，整条链路就断了；反过来，它能被单独跑通、单独验收。**

> **为什么按链路而不是按模块推进**：模块是代码的切法，链路是**能跑的东西**的切法。按链路可以一条一条打通、一条一条验收，而不是"整个系统写完才知道行不行"。答辩时能演示什么，本质就是"跑通了哪几条链路"。

### 13.2 九条链路

| # | 类别 | 链路 | 输入 → 输出 | "跑通"标志 |
|---|---|---|---|---|
| **L1** | 离线·核心 | 药品骨架导入 | OpenCMKG 的 `triples.txt` / `entities_dict.txt` → 疾病/药物/症状节点与关系（**必须用 `csv` 模块**，13 类关系） | 能查到"高血压 → 推荐药物" |
| **L2** | 离线·核心 | 药物相互作用导入 | DDInter 的 8 个 CSV + 中英药名映射 → `INTERACTS_WITH` 边（**按无序药对去重**，属性只有 `level` + `source`） | 能查到"华法林 ↔ 乙酰水杨酸"的**等级（实测 Major）**。机制与处理建议**不在 CSV 里，已按方案 A 移出交付范围**（见 §5 注） |
| **L3** | 离线·核心 | 说明书采集 | 30–50 种高危药名单 → 本地存档的说明书文本（含 URL、采集日期） | 拿到 N 篇可追溯的说明书 |
| **L4** | 离线·核心 | 说明书知识抽取 | 说明书文本 → `CONTRAINDICATED_FOR` / `CAUTION_FOR` 关系入图 | 能查到"华法林 → 孕妇禁用" |
| **L5** | 在线·核心 | 问答 | 用户问题（+会话ID）→ 回答 + Cypher + 证据子图 | 问"高血压能用什么药"能给出有依据的回答 |
| **L6** | 在线·核心 | 用药安全校验 | 药箱里的药 → 分级风险卡片 | 药箱放华法林+阿司匹林，提示 Major 风险 + 替代药 |
| **L7** | 支撑 | 会话管理 | 用户操作 → 会话与消息持久化 | 刷新/重登不丢历史 |
| **L8** | 评测 | 图谱质量校验 | 已入库图谱 → 节点/边统计与抽样错误清单（**靶点已明确**：人名噪声、剂型分裂、拼接垃圾、OOV 实体、自环） | 输出质量报告表，并可视化于"数据看板"页 |
| **L9** | 评测 | 测试集评测 | 冻结的测试集 → 准确率等指标 | 跑出消融实验对比数字 |

### 13.3 边界说明

**「按疾病推荐药物」不单独成链，并入 L5。** 理由：它走的是与 L5 完全相同的六步流程，只是 Cypher 不同。把它当独立链路会造成重复劳动。

**不做管理端，也不做数据上传。** 图谱中的药品、疾病、相互作用全部由离线管线（L1/L2/L4）写入，从不经过前端；用户往药箱里加药是"从已有 `Drug` 节点中检索并选中"，存入的是用户与药品的关联关系，**不往图谱里加任何数据**。

> 为什么不让用户上传药品：① 数据质量失控（无人审核，一条错误的禁忌关系会被系统当作事实输出）；② 摧毁可追溯性（用户上传的数据无来源、无版本，与"每条回答附证据"的核心设计冲突）；③ 医疗责任性质改变；④ 论文里这属于 CRUD，写不出研究贡献。
>
> 用户查的药不在图谱里怎么办：实体链接置信度低 → **澄清反问**；图谱中确实没有 → 明确回答"**图谱中无相关记录**"，**绝不臆造**。

### 13.4 依赖与开发顺序

```
                    ┌─── L3 说明书采集 ──→ L4 说明书知识抽取 ──┐
                    │        （并行启动，提前期最长）            │
L1 药品骨架导入 ────┼─── L2 药物相互作用导入 ──────────────────┼──→ L5 问答 ──→ L9 测试集评测
                    │                                          │
                    └─── L7 会话管理（最小版）──────────────────┘
                                                                   └──→ L6 用药安全校验
                                                                          L8 图谱质量校验
```

**主线**：`L1 → L7（最小版） → L5`

**并行启动**：`L3`（说明书采集）

**两条关键判断**：

1. **L3 是全项目"提前期"最长的一环**——限速抓取、逐条人工确认、目标 30–50 篇，还要留出被反爬拦住的缓冲。但它**不依赖任何其他链路**（只需一份药品名单）。所以必须**从现在起并行启动**，否则整条链会卡在采集上。
2. **L5 是技术风险最高的一环**——实体链接与 Text2Cypher 是整套方案里最可能走不通的两步。数据做得再全，这两步跑不通系统就没有出口。**越早跑通越好。**

**L7 排在 L5 前面的唯一理由**：L5 要把每一轮的问题、改写、Cypher、回答落库（这些是 L9 的数据来源），所以数据表和写入接口必须先存在。**但不等于要把整套会话 UI 也提前做掉。**

### 13.5 验收标准

**原则：只给两条高风险链路定量，其余定性（链条不断、能出正确结果即算通过）。**

理由：全部定量会把自己卡死（"问答准确率必须≥90% 才准往下做"很可能永远达不到）；全部定性又会出现"看着能跑、其实数据是废的"。

#### L2 —— 药名映射覆盖率（**双口径统计**）

| 口径 | 计算方式 | 用途 |
|---|---|---|
| **全量** | 映射成功数 / 1833 | ① 论文"实体对齐"章节的数据质量数字；② 预估 `Drug` 节点规模与可演示的 DDI 边数量；③ **方法有效性的信号**——异常低说明不是"罕见药映射不上"，而是映射方法本身有问题 |
| **Major 级** | Major 级相互作用涉及的药物中映射成功的比例 | ① **业务可用性判据**——药箱能不能用只取决于常见药；② **门槛卡在这里**；③ 决定演示成败 |

**为什么必须两个一起看**：

| 全量 | Major 级 | 说明什么 | 该做什么 |
|---|---|---|---|
| 高 | 高 | 方法有效、业务可用 | 继续，无需动作 |
| **低** | **高** | 罕见药/未上市药映射不上，常见药没问题 | **不用降级**，论文里把低覆盖解释清楚即可 |
| **高** | **低** | 反常：方法偏向简单药名，Major 药反而漏了 | 查 Major 药的名称形态（复方名、盐形式、商品名） |
| 低 | 低 | 存在系统性问题 | 停下，重做映射方案 |

> **门槛的具体数值，等第 0 步实测出数之后再定——不出数不拍脑袋。**

#### L4 —— 说明书抽取质量

| 指标 | 规模 | 怎么测 |
|---|---|---|
| **忠实度** | 抽 100 条 | 逐条回**说明书原文**查证"这条关系是不是原文写的" |
| **完整性** | 抽 10–20 篇 | 人工通读整篇说明书，列出应抽出的条目，再与抽取结果比对 |

> **关键认知**：忠实度是**查证题**而非医学判断题——判断依据是"原文有没有这么写"，不是"医学上对不对"。因此**不需要医学背景即可独立完成评测**，而这恰恰是大模型抽取最该被质疑的角度。

### 13.6 第 0 步（开发前先做）

**全量翻译 1833 个英文药名 + 抽 200 个人工核对**，预计半天到一天。

产出三样：
1. 全量口径与 Major 级口径的**真实覆盖率**
2. 抽检 200 条的**映射准确率**
3. **可直接复用的中英药名映射表**（L2 入库时要用）

> 收益：风险最早暴露，且几乎不浪费工作量——映射表本身是必需品。

### 13.7 链路之间的接缝

**L4 的药名接缝（最容易出问题的地方）**：说明书里写"阿托伐他汀钙片"（含盐形式 + 剂型），骨架图谱里可能是"阿托伐他汀"，另有大量商品名。所以 L4 的输出**必须先做归一化 + 匹配**：

```
抽取出的药名
  → ① 归一化：去掉剂型后缀（片/胶囊/注射液…）与盐形式（盐酸/钠/钾…）
  → ② 三级匹配：精确名 → 别名表 → 模糊匹配
  → ③ 对不上的：新建 Drug 节点，并标记 source=说明书抽取
```

**选择"新建节点"而不是"丢弃"的理由**：不丢数据；来源标记让节点随时可按来源过滤；**孤儿药比例本身是论文里一个可报告的数字**。

> ✅ **已被实测证实**：OpenCMKG 的 4,289 个药物实体中 **78.1% 带剂型后缀**，
> 且同一主成分最多分裂成 7 个实体（利巴韦林 → 胶囊/颗粒/滴眼液/泡腾颗粒/…）。
> 若不先归一化，映射覆盖率会被系统性低估。见 [`docs/数据源实测报告.md`](数据源实测报告.md) §2.7。

### 13.8 离线链路的组织形式

**L1–L4 四条离线链路会被反复重跑**（改了映射表、修了 prompt、补了说明书都要重来）。因此：

| 约定 | 做法 | 解决什么问题 |
|---|---|---|
| 独立脚本 | 每条链路一个可独立执行的 CLI 脚本 | 改一个 prompt 不必全量重跑；某一环报错不卡死整条链 |
| 幂等写入 | Neo4j 写入一律用 `MERGE`，禁止 `CREATE` | 重跑不会产生重复边 |
| 统一来源标记 | 每条链路写入的节点/边带 `source` 属性 | 可单独回滚某条链路的产出；出问题能定位到哪一轮 |

> 收益：论文里可以正当地写"数据管线可复现"。

## 14. 开发流程约定

> 本节是**协作契约**：每个模块都按这条线走，不符合流程的产出不算完成。

### 14.1 核心流程

```
① 从 main 拉分支        git switch main && git pull && git switch -c <类型>/<简述>
② 在分支上写代码
③ 自己先测一遍          按 14.3 的"自测标准"，并把证据留下来
④ 通知可以手测         附：改了什么 / 怎么启动 / 测什么 / 预期结果 / 自测证据
⑤ 用户手动再测一遍
⑥ 用户确认无误
⑦ 合回 main            先本地提交，再推远程
⑧ 删除已合并的分支
```

### 14.2 分支命名

| 类型 | 格式 | 例子 |
|---|---|---|
| 新功能 / 模块 | `feat/l<链路号>-<简述>` | `feat/l1-skeleton-import` |
| 修 bug | `fix/<简述>` | `fix/entity-link-timeout` |
| 文档 | `docs/<简述>` | `docs/chain-definition` |
| 数据管线 | `data/<简述>` | `data/drug-name-mapping` |
| 实验 | `exp/<简述>` | `exp/mapping-coverage` |

**纯文档（`.md`）改动可直接提交到 `main`**，不必开分支——它不产生可运行代码，"隔离不稳定代码"的收益在这里不存在。

### 14.3 「自测通过」的标准

**这条必须具体，否则"我测过了"无法验证。**

| 链路类型 | 自测内容（缺一不可） |
|---|---|
| 离线数据管线（L1–L4、L8） | 用样本跑通脚本；打印关键统计（处理条数 / 失败条数）；把输出前若干行贴出来 |
| 后端接口（L5–L7） | 给出**可直接执行的 curl 命令** + 实际返回的 JSON |
| 前端页面 | 截图 + 操作路径说明 |
| 数据质量类（L2 覆盖率、L4 抽取） | 量化数字（覆盖率 / 准确率）+ 抽样对照表 |

**底线三条**：

1. **不把没自测过的东西交出去**——包括"应该能跑"这种判断
2. **不能只说"完成了"，要给可复现的证据**（命令 + 输出）
3. **自测失败就在同一分支继续改，不到通过不通知**

### 14.4 提交信息规范

```
<类型>: <一句话说明>

<可选正文：为什么这么改、踩了什么坑>
```

类型：`feat` 新功能 / `fix` 修 bug / `docs` 文档 / `refactor` 重构 / `data` 数据管线 / `exp` 实验

### 14.5 合并与推送

**合并方式：普通 merge（非 squash、非 --no-ff），合并后删除分支并回到 `main`。**

完整命令序列：

```bash
# ── ① 开始一个新模块 ──────────────────────────
git switch main
git switch -c feat/l1-skeleton-import

# ── ② 写代码、自测 ────────────────────────────
git add -A
git commit -m "feat: 实现 OpenCMKG 导入脚本"

# ── ③④⑤⑥ 通知用户手测，等确认无误 ──────────────

# ── ⑦ 合回 main 并推送 ────────────────────────
git switch main
git merge feat/l1-skeleton-import
git push

# ── ⑧ 删除已合并的分支 ────────────────────────
git branch -d feat/l1-skeleton-import
```

**⚠️ 关于快进（fast-forward）**：普通 merge 在 `main` 期间**没有前进过**时会**直接快进**——不产生合并提交，分支上的每个提交原样落到 `main` 上。这意味着：

- 好处：历史是线性的，`git log` 干净好读
- 代价：**分支上所有中间提交都会进 `main`**（普通 merge 不会压缩）

> 因此**在分支上要克制提交频率**，别把"改个错别字""再试一次"这类噪音提交留给主干。一个模块的分支，提交次数控制在 1–3 次比较合适。

**其他约定**：

- 合并前 `main` 必须干净（`git status` 无未提交改动）
- 分支只存在本地，**不推远程**；远端只保留 `main`
- 如果你在别的电脑上也提交过，拉分支前先 `git pull`
- **推送需要梯子**：全局 git 配置了 `http.proxy = 127.0.0.1:7897`，代理未开时 `git push` 会连接失败（`commit` 不受影响）

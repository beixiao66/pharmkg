## 1. 你问的那条：说明书来源 NMPA → 丁香园

### 结论：**代码已经换成丁香园，但 Word 文档一个字都没改。**

**代码里的证据**（`scripts/collect_inserts.py` 开头就写着）：

```
丁香园 · 用药助手（drugs.dxy.cn）。
基线原本写的是"NMPA 官网逐条说明书"。实测 NMPA 挂在阿里云 WAF 后面，
而 NMPA 的公开库本身也只是注册信息（批准文号/厂家/剂型），并非说明书全文库。
丁香园用药助手公开可访问、无 WAF，说明书正文完整，
⚠️ 可信度边界（论文里要如实写）：丁香园是聚合平台，属二手转录，
非 NMPA 批准的监管原件；且网页版对【注意事项】【用法用量】有登录墙。
```

**采集产物里的证据**（`data/collected/index.csv` 第 1 行）：

```
url = https://drugs.dxy.cn/pc/drug/pIebEDrFip39dwRT8kgS-Xg?ky=西尼莫德
approval_date = 2020年5月7日    revision_date = 2023年8月1日
holder = Novartis Pharma Schweiz AG    manufacturer = Novartis Pharma Stein AG
```

即：**内容来自丁香园，但批准文号日期与持有人/生产企业字段仍然记录着**——这是好事，
说明"二手转录 + 监管元数据可追溯"这个组合是成立的。

**Word 文档里说 NMPA 的地方有 4 处**（都要改）：

| 位置 | 原文 |
|---|---|
| 3(1) 研究内容 | 「以**国家药品监督管理局**公开的药品说明书为语料」 |
| 4.1 研究方案 | 「禁忌与特殊人群用药信息则以**国家药品监督管理局**公开渠道的药品说明书为语料」 |
| 5(2) 数据资源条件 | 「药品说明书可通过**国家药品监督管理局**公开渠道获取」 |
| 6.2(4) 解决措施 | 「**说明书采集**严格遵守限量限速原则……记录采集来源与时间」——来源没写具体 |

### 为什么不能只把"NMPA"替换成"丁香园"

**这条实质改变的是"证据的性质"，不是名字：**

| | NMPA（原计划） | 丁香园（实际） |
|---|---|---|
| 性质 | 监管机构公布的**原件** | 聚合平台的**二手转录** |
| 权威性 | 法定文本 | 转录可能有出入 |
| 完整性 | ——（其实 NMPA 公开库只有注册信息，**没有说明书全文**） | 正文完整，但【注意事项】【用法用量】有登录墙 |

**建议改法**（可直接抄进文档）：

> 药品说明书正文取自**丁香园·用药助手**（`drugs.dxy.cn`）公开页面。原方案拟采用
> 国家药品监督管理局（NMPA）公开渠道，实测两点不成立：其一，NMPA 站点置于
> 阿里云 WAF 之后，程序化访问受限；其二，**NMPA 公开库的内容是注册信息
> （批准文号、厂家、剂型），并非说明书全文库**，无法满足抽取需求。
>
> 采用丁香园带来一个**必须声明的局限**：它属聚合平台，为**二手转录**，非监管原件。
> 为此在采集清单中同时记录**核准日期、修改日期、上市许可持有人与生产企业**
> （见 `data/collected/index.csv`），使每条抽取结果都能回溯到具体条目与日期；
> 且【注意事项】【用法用量】两节受登录墙限制，覆盖率已在清单中逐条标注。
> **本课题的抽取结论只在这 36 份样本的范围内成立。**

## 2. 另外 5 处"文档与实现"的实质冲突

### 2.1 大模型：文档写 DeepSeek，实现只用阿里云百炼

- **文档 4.1**：「通过统一的模型服务抽象层调用 **DeepSeek、阿里云百炼**等大语言模型接口」
- **实现（决策 #22）**：**只用阿里云百炼 `qwen-plus`，明确不引入 DeepSeek**。
  理由是大学生认证额度 + 一个 key 覆盖对话，**变量最少**；provider 抽象层保留，
  用于同厂商多模型对比。
- **改法**：把「DeepSeek、阿里云百炼等」改成「阿里云百炼（`qwen-plus`），
  保留模型服务抽象层以便同厂商多模型对比」。§1.1 里「以 DeepSeek 等为代表」
  是**背景引用**，可以保留不动。

### 2.2 实体链接：文档写"向量相似度兜底"，实现**明确不用向量**

- **文档 4.1**：「实体链接采用**别名词典精确匹配优先、向量相似度兜底**的两级策略」
- **实现**：`l5_entity_linking.py` + `build_drug_name_mapping.py` 用的是
  **别名表精确 → 前缀补全（AUTOCOMPLETE）→ 编辑距离**，而且代码里写了理由：
  > 「**不用向量**。药名匹配是字符串与别名问题，不是语义问题——用户输入的是药名」
- **改法**：改成「别名/前缀/编辑距离三级匹配，**不使用向量相似度**；
  原因是药名匹配本质是字符串与别名问题，向量会把"阿司匹林"与"对乙酰氨基酚"
  拉到相近位置（同类解热镇痛药），反而制造错误匹配」。
  **这是一处"实现比文档更好"的差异，写进论文是加分项。**

### 2.3 DDInter 的"机制 / 处理建议 / 替代用药"：**批量数据里根本没有这些字段**

- **文档 4.3(4)**：「提示内容包括药物相互作用的风险等级、**作用机制、处理建议与替代用药**」
- **实现**：`data/raw/ddinter/*.csv` 的**表头只有 5 列**：
  ```
  DDInterID_A, Drug_A, DDInterID_B, Drug_B, Level
  ```
  **没有**机制、管理建议、替代用药字段。DDInter 官网的配对详情页有这些内容，
  但**批量下载文件里没有**，所以实现**无法**提供。
- **改法**：把预期目标(4)改成「提示内容包括**风险等级**与**来源**」；
  机制/处理建议/替代用药列为**数据源限制**（可写成"DDInter 网页端提供而批量文件不含，
  故未纳入本系统"），或者后续按需逐条抓取配对详情页（工作量另计）。
  ⚠️ **这条如果不改，答辩问"你的机制说明在哪"就答不上来。**

### 2.4 多轮改写触发条件：文档"仅在指代/省略时触发、已含实体则跳过"，实现"一律改写"

- **文档 4.1**：「查询改写**仅在问题包含指代或省略时触发**」
- **文档 6.2(4)**：「当问题中**已包含明确的药物实体时跳过改写**」
- **实现（决策 #39）**：多轮**一律改写**，不跳过。
- **实测数据站在实现这边**：
  ```
  as-written（旧规则：按需改写）  18/23 = 78.3%
  never（新规则：一律改写）       22/23 = 95.7%
  不改写                         1/23 =  4.3%
  ```
- **改法**：两处都改成"一律改写"，并把这三个数写进文档。
  **这是文档里唯一一处被实测数据推翻的设计**，写进去比藏起来有说服力。

### 2.5 别名"存入别名属性"：文档说存进 Drug 节点属性，实现是脚本侧索引（**待确认**）

- **文档 3(2)**：「以中文通用名作为药物实体的主键，将商品名、英文名与**别名统一存入别名属性**」
- **实现**：别名来自 OpenCMKG 自带的 `SameAs`（两端都是 drug 的那些），
  在 `build_drug_name_mapping.py` 里构建成 `alias → 规范名` 的**索引**。
  是否同时写进 Drug 节点的属性——**Neo4j 当前未运行，我没法确认**，标为待确认。
- **改法**：若确实没落到节点属性，就把文档改成"别名以索引形式构建并可持久化"。

### 格式未被改动的证据

| 检查项 | 结果 |
|---|---|
| 22 个内部条目中除 `word/document.xml` 外 | **全部逐字节一致**（`styles.xml`/`settings.xml`/`footer1.xml`/`fontTable.xml`/`theme1.xml`…） |

其余 run 一字不动。

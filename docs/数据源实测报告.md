## 2. OpenCMKG 实测

### 2.1 `entities_dict.txt` —— 单行 Python 字面量，且有**三处上游 bug**

整个文件是**一行** Python dict 字面量，1.47 MB 全在第一行，必须用 `ast.literal_eval` 解析。

| 类型 | 实体数 | 样例 |
|---|---:|---|
| `producer` | 16,772 | 帅乐氟哌噻吨美利曲辛片、南通百益麝香壮骨膏 |
| `symptom` | 16,197 | 纤毛结构缺陷、背也疼、脸很烫 |
| `disease` | 14,726 | 左边身子疼、鼻塞严重、大便不尽 |
| `food` | 4,846 | 黄芪茶、火腿鸡块粥 |
| `drug` | 4,289 | 盐酸二甲双胍肠溶片、谷氨酰胺 |
| `check` | 3,214 | 左肾静脉"胡桃夹"综合征检查、血凝试验、浮髌试验 |
| `treatment` | 598 | 手术治疗为主,若失去手术时机,可药物支持性治疗 |
| `department` | 54 | 风湿免疫科、神经内科 |
| **合计** | **60,696** | |

> ✅ 这个总数**与基线 §3 原本写的 60,696 完全一致**——说明基线那个数字是对的，
> 而本报告上一版算出的 53,863 才是错的（原因见下面第 ② 条）。

#### ⚠️ 上游的三处 bug（读取层 `scripts/opencmkg_io.py` 已修复并计数）

**① 裸标识符 `nan`** —— 上游把 pandas 的缺失值直接 `str()` 写进了文件，会让
`ast.literal_eval` 抛 `ValueError`。用 `__NAN__` 占位替换并计数。

**② 嵌套 list（最严重，会造成实质性数据丢失）**

`symptom` 列表里塞了**一个内层 list**，装着 6,833 个条目。上游把一整批实体
当成**单个元素**了。后果有两层：

- 不展平 → 这 6,833 个条目等同于不存在；
- 用 `str()` 强转 → 造出一个 **71,618 字符**的"症状名"，
  **直接撑爆 Neo4j 的索引长度上限**（实测报 `Property value is too large to index`）。

而且**上游给这批条目标的类型是错的**。实测证据：

| 内容 | 数量 | 判定依据 |
|---|---:|---|
| 检查项（`血凝试验`、`CT造影增强扫描`、`睾丸活检`） | 3,214 | 47% 是 `disease_need_check` 的尾实体，且占全部检查项尾实体的 **95.9%** |
| 患者口语（`拉一次粑粑`、`姨妈推迟半个月没来`） | 3,620 | 未被任何关系引用 |
| —— | **0** | 出现在 `disease_has_symptom` 里的数量 |

整体当 `Symptom` 入库会造成 **4,985 个同名双标签节点**（同一名字既是 `Symptom`
又是 `Check`）。因此本项目**按关系证据逐条归位**：是 `disease_need_check`
尾实体的 → `Check`，其余保留上游标注的 `Symptom`。修复后双标签降到 26 个
（残留的是原本症状词表里的污染，与嵌套 list 无关）。

**③ 展平后的重复项** —— 顺序保留地去重（本数据实测为 0 个）。

### 2.2 `triples.txt` —— 解析陷阱（**L1 最容易踩的坑**）

- 编码 UTF-8，LF 换行，**无表头**，格式为 `头实体,关系,尾实体`
- 354,755 行，全部可解析，**0 行重复**，474 条自环

**关键**：字段本身含逗号时会**加双引号**，但只给需要的字段加。三种真实形态：

```
百日咳,disease_need_check,"耳,鼻,咽拭子细菌培养"          ← 尾部带引号
"跖骨,趾骨骨折",disease_has_symptom,疲劳                  ← 头部带引号
"小儿人类疱疹病毒6,7,8型感染性疾病",disease_has_symptom,疱疹
```

三种解析方式的实测后果：

| 解析方式 | 有效三元组 | 后果 |
|---|---:|---|
| `line.split(",")` | 352,584 | **静默丢掉 2,171 行**（0.61%） |
| `line.split(",", 2)` | 354,755 | 数量对了，但**内容错位**——头部带引号的行被切成 4 段，造出 `趾骨骨折"` 这种不存在的关系名，污染 13 类关系统计 |
| **`csv.reader`** ✅ | **354,755** | 全部正确 |

> **教训**：`split(",", 2)` 这种"看起来能救回来"的写法最危险——它不报错，
> 但把错误藏进了关系字段里。**必须用 `csv` 模块**，并把"逗号数 ≠ 2 的行数"作为质量指标留下来。

### 2.4 数据质量问题（有证据，不是"可能有"）

骨架图谱**不干净**。三类问题，都有具体条目可查：

**① 人名与口语描述混进了医学词汇表**

| 噪声条目 | 性质 | 出现在 |
|---|---|---|
| `毓卓` | 人名 | **55 个疾病**的症状位 |
| `闫鹏辉` | 人名 | 15 个疾病的症状位 |
| `左边身子疼`、`肚子一痛`、`刀口有点疼` | 患者口语 | `disease` 词表 |
| `体重降了28斤`、`背也疼` | 患者口语 | `symptom` 词表 |

关键点：`毓卓`、`闫鹏辉` **在 `entities_dict['symptom']` 里是"合法"的**——
说明污染发生在**词表构建阶段**，不是后来插入的。这解释了 QAKG 的数据来源：
它源自 39 健康网 / 寻医问药的患者问答，医生署名和患者口语被一起抓了进来。

**② 同一主成分因剂型分裂成多个实体**

| 主成分 | 分裂条数 | 变体 |
|---|---:|---|
| 利巴韦林 | 7 | 胶囊 / 颗粒 / 滴眼液 / 泡腾颗粒 … |
| 阿昔洛韦 | 7 | 乳膏 / 滴眼液 / 胶囊 / 分散片 … |
| 格列吡嗪 | 5 | 分散片 / 片 / 缓释片 / 控释片 |

→ 做药名映射前**必须先归一化**（剥离剂型、盐形式），否则同一个药会被算成多个实体，
覆盖率会被系统性低估。

**③ 拼接垃圾**

`盐酸普萘洛尔片盐酸地尔硫`、`佛山)药业伤科跌`、`6-二磷酸果糖"`、`C颗粒"` ——
明显的爬取截断/拼接产物。

**④ 量化指标**

| 指标 | 数值 |
|---|---:|
| `disease_has_symptom` 症状实体数 | 6,673 |
| 只挂在 1 个疾病下的症状 | 1,333（20.0%） |
| 不在 `entities_dict['symptom']` 里的症状 | 938（14.1%） |
| 自环（头 == 尾） | 474 |
| 同名却出现在多个关系类型里的节点 | 1,771 |

> 最后一项**不是缺陷，是上游数据的固有歧义**——同一个名字在不同关系里扮演不同角色：
> `木瓜` 既是食物又是药、`谷氨酰胺` 既是药又是化验项、`紧张` 既是疾病又是症状。
> 关系把名字断言成某个类型，就该建那个类型的节点（把 `HAS_SYMPTOM` 的尾接到
> `:Disease` 节点上反而更错）。本项目所有查询都带 Label，因此不受影响。
> 分布：`Disease+Symptom` 1,022、`Drug+Producer` 534、`Check+Drug` 82、
> `Drug+Food` 26、`Check+Symptom` 24，其余零散。

> **对本项目的意义**：这不是坏消息，是**好消息**。
> 基线 §12 里"这张图谱是你建的吗"的答辩要点，现在有了硬证据支撑：
> 骨架有多源、有噪声、有实体分裂问题，而我要做的是**多源融合 + 实体对齐 + 质量校验**。
> L8（图谱质量校验）从"锦上添花"升级为"必要的、可量化的增量工作"。

### 2.5 `SameAs` 关系 —— 白送的实体对齐数据

17,977 条 `SameAs` 三元组，涉及 17,351 个不同实体。样例：

```
下肢疼痛  ↔  下肢困痛不适
下肢疼痛  ↔  腿会疼
下肢疼痛  ↔  腿疼
下肢疼痛  ↔  右腿痛
```

**这是一条现成的同义词/实体对齐链路**，可以直接支撑 L4 的实体链接：
做监督信号、做评测参照、或至少做 few-shot 示例。覆盖面很广——
**17,350 个实体（100%）都能在 `entities_dict` 里找到类型**，43,346 个实体未被
任何 `SameAs` 引用。

> ⚠️ 第一版报告写的是"79% 能对上、40,133 个未被引用"——**那是嵌套 list bug 造成的假象**
> （被埋掉的检查项和口语症状都算成了 OOV）。修好后端点可解析率是 100%，
> 17,977 对里只有 **3 对**因为端点确实不在词表里而跳过。

### 2.6 `manual_annotation.csv` —— 现成的实体对齐金标准

| 项 | 值 |
|---|---|
| 列名 | `实体1,实体2,标注结果`（带 BOM） |
| 条数 | 852 |
| 标注分布 | 1（同一实体）560 条 / 0（不同实体）291 条 / 空 1 条 |

```
妊娠合并糖尿病    | 妊娠期糖尿病        → 1
急性淋巴细胞性白血病 | 急性淋巴细胞白血病   → 1
体质性低血压      | 体位性低血压        → 0    ← 注意：名字像，但标注为"不同"
```

> **用途**：基线 §7 里"药名映射质量"要抽 200 个药名人工核对——
> 现在有一份**他人已标注的 852 条实体对齐数据**，可直接用来评测实体链接模块，
> 比自己临时标注更可信、更省时间。这是本次体检最大的意外收获。

## 3. DDInter 实测

### 3.1 列名 —— 只有 5 列（**推翻基线的核心假设**）

8 个文件列名完全一致：

```
DDInterID_A, Drug_A, DDInterID_B, Drug_B, Level
```

```
DDInter58,Aluminum hydroxide,DDInter582,Dolutegravir,Major
DDInter112,Aprepitant,DDInter582,Dolutegravir,Minor
```

⚠️ **没有 `mechanism` / `description` / `management` / `alternative_drug`。**

基线 §5 的 `INTERACTS_WITH` 边定义了 6 个属性，§13 的 L2 验收标准要求
"能查到等级、机制与处理建议"——**后三者根本不在 CSV 里**，
只存在于 DDInter 网站的药物详情页（需另外爬取）。

### 3.2 规模与去重

| 指标 | 实测 | 基线声称 |
|---|---:|---:|
| 原始记录总数 | 222,383 | 236,834 |
| **去重后无序药对** | **160,235** | — |
| 重复记录 | 62,148 | — |
| 药物 ID 数 | 1,939 | 1,833 |
| 同一 ID 多种写法 | 0 | — |

**分片规则未解**。两个假说都被实测否定：

- 假说一「按药名首字母分片」：各文件首字母命中率只有 3%–22% → **否定**
- 假说二「按药物分片（每药只属一个文件）」：只有 4.2% 的药只出现在 1 个文件 → **否定**

字母 code 的确切含义未知（可能是药理分类，但没有公开对照表）。
**但这对工程没影响**：不管 code 是什么，都必须按 `frozenset(Drug_A, Drug_B)` 去重，
否则 62,148 条重复记录会变成图谱里的重复边。

### 3.3 严重程度分布

| Level | 记录数 | 占比 | 去重后 | 占比 |
|---|---:|---:|---:|---:|
| Moderate | 130,367 | 58.6% | 96,675 | 60.3% |

### 3.4 药名写法 —— L2 验收标准的坑

| 搜索词 | DDInter 中的匹配数 |
|---|---:|
| `aspirin` | **0** |
| `acetylsalicylic` | 1 → `Acetylsalicylic acid` |
| `warfarin` | 1 → `Warfarin` |

含 Warfarin 的记录 1,256 条，其中 Major 级 173 条。

> **教训**：药名映射表必须按 DDInter 的**实际写法**建（含 `(topical)` 这类修饰、
> 用 `Acetylsalicylic acid` 而非 `Aspirin`），不能凭常识或英文词典推。

### 9.2 解析器四处缺陷

#### ① 换行丢失（最严重）

站点把排版**全部放在标签上**，而这三样**都不产生文本节点**：

| 排版 | 实际写法 |
|---|---|
| 段落 | `<div>` |
| 段内换行 | `<p class="new-line"></p>`——**空** `<p>`，靠 CSS 撑开 |
| 列表项 | `<li>` |

旧解析器只把 `handle_data()` 收到的文本拼起来，于是所有边界都没了。
详情页 449,733 字符里**只有 6 个换行符**——页面本身是压缩成一整行的。

最典型的受害者是【禁忌】。乌帕达西替尼原文是 4 条独立的 `<li>`：

```html
<ul><li>对本品活性成份或任何辅料过敏者禁用</li>
    <li>活动性结核病或活动性严重感染</li>
    <li>重度肝功能损害</li>
    <li>妊娠</li></ul>
```

旧产物把 4 条焊成一行、**零分隔符**：

```
对本品活性成份或任何辅料过敏者禁用活动性结核病或活动性严重感染重度肝功能损害妊娠
```

**修法**：块级标签（`div` / `p` / `li` / `ul` / `table` / `h1`–`h6` / `br` …）
**进出各发一个换行**；行内标签（`span` / `i` / `u` / `strong` / `sub` / `font` …）不发。

#### ② 小节白名单**静默丢弃**了 56 个小节

旧代码只把 `SECTIONS` 列表里列到的小节写进 txt，而那份名单漏了
【临床试验】【毒理研究】【用药须知】【化学成份】——这 4 个小节于是
**在产物里整节消失**，可 `index.csv` 的 `sections` 列**照旧列着它们**。
**元数据说有、产物里没有**，比单纯缺数据更危险：任何按清单去取小节的
下游代码都会拿到空字符串，而且不会报错。

**修法**：按 HTML **文档顺序全部写出**；白名单降级为"有没有出现没见过的节名"
的报告项，既不参与过滤、也不参与排序。

#### ③ 空标签让 depth 漂移

`HTMLParser` 不认识自闭合标签：`<br/>` 会同时触发 `handle_starttag` 与
`handle_endtag`，而 `<br>` **只触发前者**。旧代码无条件 `depth += 1 / -= 1`，
depth 会一路偏掉，小节边界随之错位。

**修法**：显式维护 `VOID_TAGS`（`br` / `hr` / `img` / `input` …），空标签不改变层级。

#### ④ 表格被拍成"每格一行"

站点用的是真 `<table>`。只修了换行之后，`td` / `th` 也按块级标签各发一个换行，
于是表格变成一串竖排的单元格，**行列对应关系全部丢失**。实测 36 份里共 **136 张表**：

| 小节 | 表数 |
|---|---|
| 临床试验 | 86 |
| 不良反应 | 24 |
| 用法用量 | 21 |
| 药代动力学 | 3 |
| 药理作用 | 1 |
| **注意事项** | **1** |

关键的【禁忌】**一张表都没有**；落在 L4 抽取目标（禁忌 / 注意事项 / 儿童用药）里的
只有 **1 张**——`巴瑞替尼.txt`【注意事项】的"表 2. 实验室测量值和监测指南"。

**为什么非修不可**：空单元格不产生任何文本，拍平之后**分不清"原文就是空"与
"解析掉了"**——与【禁忌】= `无` 是同一类诚信问题。

**修法**：**一行表格行 = 一行文本**；第 2 格起发 ` | `（**空单元格照发**），
行结束发换行；格内的 `<br>`（一格常列多个条目）换成 `；`，以免把这一行拆散。

### 10.1 朴素基线冻结（第一层：抽取）

36/36 跑通，**451,484 输入 tokens / 3,375 输出 / 115.7 秒 / `finish_reason` 全 `stop` / 0 失败**，
成本约 ¥0.36（约占 `qwen-plus` 免费额度的 45%）。产物、提示词、参数、原始输出全部存档。

在 11 篇人工标注的评测集上，**原子级 P = R = F1 = 1.000**（77 个原子）。

> **满分必须先证明它不是恒真的。** 机械的顿号切分会让金标准和输出**对称地**碎掉，
> 两边碎法一样就永远"全中"。所以另跑了一次**错位对照**：把输出整体挪一格再评，
> 得到 TP 0 / FP 52 / FN 77 → **F1 = 0.000**。指标会动，满分是真的（至少不是恒真）。

标好即冻结：`data/eval/contraindications_gold.csv`（11 药 / 35 行）。

### 10.2 为什么必须有第二层

L4 的交付物不是"一段文字"，而是**图谱里的边**：`CONTRAINDICATED_FOR : Drug → Disease/Population`。
**"抽到了"离"进图了"还差一整步对齐**——`卒中` 得先变成图谱里的某个节点。
抽取层已经满分，所以**只报一个数就完全说不清错在哪一层**。于是新增：

```
第一层  原子级      最小并列项集合（与 score_extraction.py 同口径）
第二层  边级        (药, 节点规范名) 集合——同药同节点只算一条边
```

第二层**从 `raw/` 的模型输出走完全程**（切原子 → 逐原子对齐 → 收边），
不是从金标准原子出发——第一层的错会如实传到第二层，不做理想化。

### 10.3 对齐器：规则 77.8% → 规则 + ⑤ LLM 83.3%

分母是 **54 条入图边**（8 药 / 51 个不同的 `(药, 节点)` 对）。

| 配置 | 命中 | 准确率 | 说明 |
|---|---|---|---|
| ① **只用规则**（①②③④） | 42 / 54 | **77.8%** | 零 API 成本、完全可复现 |
| ② **规则 + ⑤ LLM 兜底** | 45 / 54 | **83.3%** | ⑤ 只对"④新建"的原子调用，结果按原子缓存 |

```
①精确✓ 26   ②包含✓ 6 / ✗ 1   ③前后缀✗ 1
⑤LLM(已存在)✓ 1 / ✗ 3    ⑤LLM(新建)✓ 12 / ✗ 3    ⑤LLM(新建·降级)✗ 1
```

**规则从 59.3% 提到 77.8%（+18.5pt），改的是四处，每一处都不是"加同义词表"：**

1. **人群受控词表补通用变体**（决策 #33）：`妊娠期妇女`/`妊娠期间`/`怀孕妇女` → `孕妇`
   等 51 种写法。**疾病侧一个字都没加**——疾病侧的近义合并是 OpenCMKG 词表自己的
   图谱质量问题，靠对齐器偷偷合并只会既掩盖问题、又在冻结的评测集上调参。
2. **人群名纳入 ②包含 匹配**，并修掉一个**真 bug**：词表条目 `大环内酯类药物过敏者`
   结尾的「者」会被 `STRUCT_WORDS` 剥掉，于是**这两条词表项从来就没可能被匹配上**
   （`对三环类药物过敏者` 反而命中了更宽的 `药物过敏`）。修法是**两侧都先归一化**，
   并且**长名优先**。
3. **归一化补上"去掉一切空白"**（含全角）。这条是**评测逼出来的**：
   `最近 6 个月内发生心肌梗死` 里的空格让**已经写好的** `最近\d+个月内` 规则整个失效。
4. **疾病词表改成"图里实际存在的节点名"**（详见 §12.3）。原先用的是
   `entities_dict["disease"]`，而 L1 写关系时还会把关系两端 `MERGE` 成节点，
   于是**图里的病名比它多 133 个**——`免疫缺陷` 就在其中，导致对齐器在
   `免疫缺陷` 已经存在的情况下"新建"出 `免疫缺陷状态`。**入库时这会变成重复节点**，
   所以这不是调参，是正确性缺陷。修完 +2 条。

> ③前后缀 那一级有**并列最高分**时会按确定性顺序取第一个（原先是 set 的迭代顺序，
> 不稳定）。实测金标准里**并列数 = 0**，所以这是**稳健性修复，不影响本次任何数字**——
> 报出来是为了不让"确定性"变成一句没验过的声明。

**⑤ LLM 兜底净赚 +3，但它会弄坏东西，如实报出来：**

```
⑤ 调用 20 条 · 救回 5 条 · 弄坏 2 条（净 +3）
   卒中                          规则 卒中            → ⑤ 改成 中风
   正在使用单胺氧化酶（MAO）抑制剂    规则 单胺氧化酶抑制剂  → ⑤ 改成 单胺氧化酶抑制剂使用期
```

被弄坏的都是**"规则照抄归一化原子名"反而正确**的情形——模型非要"规范化"，
把对的改错。这属于**该报的现象，不该靠额外裁决规则去救**：任何"什么时候听 ⑤"的
规则都会是我看着这 54 条写出来的。

**仍不对的 9 条**，性质分三类（都**不改规则**，留给 LLM 或如实报告）：

| 类别 | 例子 | 为什么不用规则救 |
|---|---|---|
| 疾病**分级** | `II 度 II 型房室传导阻滞` → `房室传导阻滞` | "要不要把二度/三度并成房室传导阻滞"是**图谱粒度决策**，不是字符串问题 |
| 近义**不同字** | `肝功能损害`/`肝功能受损`/`肝功能损伤`、`甲状腺机能亢进` | 写进规则＝在冻结评测集上调参；交给 ⑤ 并报告差值 |
| 状态后缀 | `免疫缺陷状态` → `免疫缺陷` | 剥「状态」会**连带毁掉** `癫痫持续状态` 这类真病名 |

### 10.5 三个**结构性**缺口（不是调参能解决的）

**(1) 缺"该不该进图"的判定——45 条假阳性边里有 32 条出自它**

金标准里 **9 行 `仅文本`**（"对本品任何成份过敏"这类通用过敏禁忌）和 **23 行 `删除`**
（残片、限定语、理由句）**明确不该进图**。对齐器目前**没有"不入图"这个输出**
（每个原子都会得到一个节点），于是这些原子全变成假阳性边。

**而这个判定根本不属于对齐器**——决策 #30 本来就规定：短/空禁忌**照抽但标 `generic_only`**。
也就是说缺的是**抽取层的标记**。把这一层剥掉之后（诊断上界，假设 `generic_only` 已判对）：

| 配置 | P | R | F1 |
|---|---|---|---|
| ① 规则单独 | 0.711 | 0.627 | **0.667** |
| ② 规则 + ⑤ LLM | 0.844 | 0.745 | **0.792** |

**层定位错了，力气就会全花在"改对齐器"上。** 这是本报告最该记住的一条。

**(2) 两层金标准的切分口径不一致——5 条边在第一层就注定拿不到**

抽取口径按 `、，；` 切原子；节点金标准里对 `或`/`和` **也切**。于是有 5 个抽取原子
**同时覆盖两条入图边**，那两条边**不可能**被单独预测出来：

```
伤寒疫苗：慢性疾病的急性发作期和发热者                    → 发热 / 慢性疾病
奥扎莫德：过去或目前有 II 度 II 型房室（AV）传导阻滞…        → 房室传导阻滞 / 病态窦房结综合征
来氟米特：中性粒细胞减少或因类风湿关节炎以外原因导致血小板减少   → 中性粒细胞减少症 / 血小板减少
英夫利西单抗：患有结核病或其它活动性感染（包括脓毒症…         → 活动性感染 / 结核病
阿那格雷：拉普乳糖酶缺乏或葡萄糖-半乳糖吸收障碍            → 乳糖酶缺乏 / 葡萄糖半乳糖吸收障碍
```

**第二层召回率的结构性天花板 = 46/51 = 90.2%**，剩下的不该算在对齐器头上。
要动就得**同时改两层的切分口径并重测第一层**（`atoms()` 对金标准和输出是同一个函数，
所以改切分是对称的），这属于**改冻结评测口径**，是决策不是实现。

> 这一段第一次跑出来时**两次的 SHA-256 不一样**：金标准边是个 `set`，
> "这几种边被同一个原子覆盖"的罗列顺序就随进程的哈希随机化变。已改成 `sorted`，
> 现在**连跑三次产物逐字节一致**。评分脚本自己不确定，"可复现"三个字就是空的。

**(3) `用药` 槽位与 §5 定义冲突——2 条边永远拿不到**

`奥希替尼 → 圣约翰草`、`奥扎莫德 → 单胺氧化酶抑制剂` 在节点金标准里被标成
`node_type = 用药`，但 §5 写的槽位只有 **Disease / Population**。而且 OpenCMKG 的
`drug` 词表（4,289 项）**两个名字都没有**。详见 §5 的待定说明。

### 10.6 顺带查出的上游数据质量问题（**L8 新靶点**）

`entries_dict` 的 14,726 个"病名"里混着**大量口语化病史短语和错别字**——
这不是"可能有"，扫一下就有：

```
肝功能不正正常   ← 错别字（多一个"正"）
肝功能就不正常 / 肝功能也不好 / 肝功能只是轻度异常 / 肝功能就不正常
肝功能是稍微有点异常 / 肝功也只是轻度异常
勃起不太好硬           口气也不好
听力一直不太好         月经一直就不规律        肛门内就不坠胀
```

窄模式（含 `也`/`就`/`只是`/`不太好`/`不正`/`有点`…）一扫就 **23 条**，实际只会更多。

**它直接伤害对齐**：词表越脏，② 包含匹配的假阳性越多——前面调相似度时栽的两次
（`发热 → 脸发热`、`严重慢性疾病 → 慢性`）就是这个病的症状。

> 原靶点清单是"人名噪声、剂型分裂、拼接垃圾、OOV 实体、自环"，
> 现在要补上**「口语化病史短语混入病名词表」**。

## 11. L4 消融层级 2：按小节送 + JSON 约束 + generic_only（2026-10-14）

### 11.1 为什么动的偏偏是这三个变量

§10 的结论是：**抽取层已经满分，瓶颈全在"抽出来的东西怎么进图"**，而 45 条假阳性边里
**32 条出自"金标准明确判定不该进图"的原子**。也就是说 L4 缺的不是"抽得准"，
是"抽完之后判该不该进图"。按决策 #30 这个判定属于**抽取阶段**，于是本层一次动三个
**基线故意没做**的变量（每个都是决策 #30 写下的）：

| 变量 | 基线 | 本层 |
|---|---|---|
| 输入单元 | 整篇说明书（最多 111 KB） | **整节**（【禁忌】） |
| 输出约束 | 无（自由文本） | **JSON**（`response_format=json_object`） |
| "该不该进图" | **不判** | **`generic_only` 标记** |

⚠️ **只跑【禁忌】一节。** 决策 #30 还规定了【注意事项】+【儿童用药】→ `CAUTION_FOR`，
但**这两节没有金标准**——没有金标准的产物**不可评测**，做出来只是"看起来做了"。
本层与基线的**唯一可比面就是【禁忌】**。另：**零样本**，不写 few-shot（决策 #26
严禁取自冻结测试集），提示词里写的是"通用过敏禁忌"这个**概念的定义**。

### 11.2 成本：输入降到 **3.6%**

| | 基线（整篇） | 本层（【禁忌】一节） |
|---|---|---|
| 输入 token | **451,484** | **16,385（3.6%）** |
| 输出 token | 3,375 | 4,522（1.34×，JSON 更啰嗦） |
| 调用数 / 失败 | 36 / 0 | 36 / 0 |
| 墙钟 | 115.7 s | 115.0 s |

**36 篇【禁忌】正文合计只有 3,718 字符**，而基线整篇送了 **613,345 字符**。

> ⚠️ **省的是 token 和配额，不是时间。** 两边墙钟几乎一样（115.7 / 115.0 秒）——
> 延迟由**每次调用的固有开销 + 输出长度**主导，不由输入长度主导。这点必须说清楚，
> 否则"40 倍"会被误读成"快 40 倍"。

### 11.3 第一层（抽取）：**一模一样，1.000**

两个方法都是 `TP 77 / FP 0 / FN 0`，`P = R = F1 = 1.000`；托法替布（原文【禁忌】
只有一个「无」字）也照样被正确判成"无条目"。**本层用 3.6% 的输入拿到了同一个第一层
成绩**——这本身就说明"整篇送"里 96% 的 token 是在陪跑。

### 11.4 第二层（边）：0.614 → **0.716**，而这变化**只可能来自一个变量**

| 配置 | 全部 | **剔除 `generic_only`** | 诊断上界（真值） |
|---|---|---|---|
| ① 规则单独 | P 0.416 R 0.627 **F1 0.500** | P 0.552 R 0.627 **F1 0.587** | P 0.711 R 0.627 F1 0.667 |
| ② 规则 + ⑤ LLM | P 0.513 R 0.765 **F1 0.614** | P 0.672 R 0.765 **F1 0.716** | P 0.844 R 0.745 F1 0.792 |

**关键证据：未过滤时，两个方法的第二层逐项同数**（都是预测 77 对、
`TP 32 / FP 45 / FN 19` 与 `TP 39 / FP 37 / FN 12`）。说明按小节送 + JSON 约束
**没有改变原子集合**——切出来的还是同一批 77 个原子。于是第二层从 0.614 涨到 0.716，
**只能归因于 `generic_only` 这一个变量**，不是"换了个提示词碰巧变好"。

`generic_only` 把 37 条假阳性边砍到 19 条，吃掉了到上界（0.792）**一半以上**的差距。

### 11.5 `generic_only` 标记本身准不准：**它自己的口径下 F1 = 0.941**

用金标准的「仅文本 / 删除」当答案：

```
条目级（与标记的粒度一致）  TP 8   FP 0   FN 1    P 1.000  R 0.889  F1 0.941
原子级（与边级口径一致）    TP 19  FP 0   FN 13   P 1.000  R 0.594  F1 0.745
```

**一条都没误标**——标记只要说 `true`，金标准就同意（两个口径 FP 都是 0）。
这是最该在意的方向：误标会**删掉真边**，漏标只是少删。

> ⚠️ **两个口径必须都报。** 原子级的 13 条 FN **全部是"条目被 `、，；` 切出来的残片"**
> （`且功能良好`、`除非患者体内有心脏起搏器`、`多形性红斑）的患者`…）。
> **标记是条目级的**，拿原子级去评它必然低估。只报原子级会得出"标记召回只有 59%"
> 的错误结论；只报条目级又和边级口径对不上。所以两个都摆出来。

### 11.6 剩下那 13 条假阳性边：`generic_only` **管不了**这一类

对照金标准 `reason` 列自己写的理由，23 条「删除」行长这样：

```
举例（括号内 / 「例如…」）   例如 AIDS（艾滋病）、例如患有肾病综合征、例如肝炎和结核
辅料名                      玉米淀粉 / 聚乙二醇 / 滑石粉 / 羟丙甲纤维素…（来氟米特一条里切出 7 个）
残片（切分产物）             且功能良好、多形性红斑）的患者
理由句                      因为缺乏该患者群的临床使用经验、因为制剂中含有乳糖
后果（指令本身，不是实体）     禁用本品、不应使用本品
过敏条目的一部分             对英夫利西单抗、其它鼠源蛋白或本品中任何成份过敏的患者
```

**它们不是"通用过敏禁忌"，而是"压根不是一个实体"。** `generic_only` 回答的是
"要不要进图"，这 13 条需要的是另一个判定——**这到底算不算一个实体**。

而它们的**共同根源在原子切分**：`、，；` 会把括号内举例、理由从句、后果句切成独立原子，
对齐器再给每个残片建一个节点。**下一个杠杆是切分口径，或一个"是不是实体"的判定，
而不是继续改 `generic_only` 的提示词。**

> ⚠️ **切分口径属于冻结的评测口径**：节点金标准里那些「残片」行**就是按现口径标的**
> （例如 `多形性红斑）的患者` 单独成行）。改切分＝要重标金标准并重测第一层，
> 这是**决策**，不顺手改。

### 12.2 **诚实声明：图里这批边约三成是假阳性**

入库脚本每次都会把**实测质量**打出来（从 `score_edges.json` 读，不是我手写的）：

```

→ 图里这批边约有 33% 是假阳性
```

它们带着 `align_level` 与 `confidence`（high 58 / medium 113）就是为了让下游（L6）
按可信度过滤。**不要把这批边当成 ground truth。** 这条声明同时写在脚本输出里、
边属性里和这里——**不能只写在论文里**。

### 12.3 顺带查出的三个缺陷（都不是调参能解决的）

**(1) 对齐器的疾病词表不等于图里的节点集 —— 会在入库时造重复节点**

原先用 `entities_dict["disease"]`（14,726）当目标词表，但 L1 写关系时还会把关系两端
`MERGE` 成节点，所以**图里的病名比它多 133 个**（`免疫缺陷`、`休克`、`不孕不育`、
`内出血`…）。后果：`免疫缺陷` 明明已经在图里，对齐器却"新建"了一个 `免疫缺陷状态`。
反过来 0 个（词表里的病名 100% 在图里）。

修法：词表改用 `opencmkg_io.graph_node_names("disease")` —— **本地就能算出 L1 实际写了
什么**，不需要连库。修完对齐器 **+2 条**（规则 77.8% / 规则+⑤ 83.3%）。

> 这条不是"为了让数字好看"：**入库必然造重复节点**才是发现它的原因，
> 而重复节点是图谱质量问题里最难事后清理的一类。

**(2) ⑤ LLM 会绕过受控人群词表 —— 同一件事落成两个节点**

实测 ⑤ 返回的人群名有 19 个，而受控词表只有 7 个。里面既有**同一概念的另一种写法**
（`妊娠` / `育龄期女性` / `大环内酯类抗生素过敏`，会和 `孕妇` / `育龄女性` /
`大环内酯类药物过敏者` 并存），也有**根本不是人群**的东西：

```
体内有心脏起搏器      单胺氧化酶抑制剂使用期      单胺氧化酶抑制剂用药期间
特殊人群             三唑类抗真菌药过敏          早产新生儿  …
```

修法（**评分与入库共用一份规则**，见 `align_nodes.canonical_population`）：
① 先收回受控词表（`妊娠` → `孕妇`）；
② **收不回去的一律降级成疾病节点**并**点名报出来**（实测 11 个）。

这样 `Population` 标签里**只会有我自己定义的那 5 个名字**——一个可检查的不变量。
让模型靠"我觉得这算个人群"一点点撑大受控词表，比把它降级成疾病危险得多。

**(3) 36 个说明书药名有 9 个和图里的药对不上 —— 全是 OpenCMKG 的「剂型分裂」**

```
来氟米特   → 只有「来氟米特片」              他克莫司 → 只有「他克莫司缓释胶囊」「他克莫司胶囊」
伤寒疫苗   → 只有「伤寒疫苗（减毒活）」「（灭活）」  多塞平  → 只有「盐酸多塞平乳膏」「盐酸多塞平片」
氯氮平 / 尼洛替尼 / 安非他酮 / 西沙必利 / 达沙替尼 同类
```

**处理：新建物质级节点**（`source="insert"`，并把候选名记进 `form_candidates`），
理由与决策 #27 方案 B 同一条——把一份**物质级**说明书挂到某一个**剂型级**节点上，
等于凭空断言"这个禁忌只属于那个剂型"。`伤寒疫苗（减毒活）`/`（灭活）` 更明显：
它们**本来就是两种不同的产品**，挂哪个都是错的。

这同时是 **L8 数据质量问题"剂型分裂"的第一个下游受害者**（§2.4 早有靶点记录）。

## 13. L4 验收清单：两条标准都测完了（2026-10-14）

基线 §13.5 给 L4 定了两条验收标准。**两条现在都有实测数字了**：

| §13.5 的标准 | 规模 | 做法 | 结果 |
|---|---|---|---|
| **完整性** | 10–20 篇 | 人工通读整篇，列出应抽条目，与抽取结果比对 | ✅ **11 篇**（分层抽样）人工标注金标准；第一层 `P = R = F1 = **1.000**`（77 原子），第二层边级 `F1 0.716`（§10–§11） |
| **忠实度** | 抽 100 条 | 逐条回**说明书原文**查证"原文有没有这么写" | ✅ **100 条覆盖 35 个药**：消融层级 2 = **100.0%**，朴素基线 = **94.0%**（§13.2） |

### 13.1 为什么忠实度**可以自动查**

§13.5 自己给了一条关键认知：

> **忠实度是「查证题」而非医学判断题**——判断依据是"原文有没有这么写"，不是"医学上对不对"。
> 因此**不需要医学背景即可独立完成评测**。

"原文有没有这么写"**可以变成子串匹配**：把抽出来的每条原子，拿回**模型当时看到的原文**里查。
照抄就能查到；改写、拼接、凭空补写就查不到。所以这一条既不需要医学背景，**也不需要人工**。

`scripts/check_fidelity.py` 就是这么做的，两个严格度都报：

* **严格** = 去掉一切空白后逐字匹配（只容忍换行/空格的排版差异）
* **宽松** = 再去掉全半角标点差异（容忍 `(`/`（`、`,`/`，`）

> 只报严格会把"模型把 `（` 写成 `(`"也算成不忠实（那只是排版）；只报宽松又会把
> "只是把标点重排了一遍"混进"逐字照抄"里。**两个都报**，差别本身也是信息。

### 13.2 结果：JSON 约束 + "照抄"指令带来 **94.0% → 100.0%**

```
按药轮转抽 100 条，覆盖 35 个药（§13.5 要求"抽 100 条"）

朴素基线（查证范围＝整篇说明书）    严格 94/100 = 94.0%    宽松 94/100 = 94.0%
消融层级 2（查证范围＝【禁忌】一节）  严格 100/100 = 100.0%  宽松 100/100 = 100.0%
全量 216 / 214 条：基线 严格 204 = 94.4% 宽松 205 = 94.9%（1 条只是标点写法不同）
                    消融层级 2 严格 214 = 100.0% 宽松 214 = 100.0%
```

⚠️ **查证范围必须等于"模型当时看到的输入"**：按小节送的那层只看到【禁忌】一节，
朴素基线看到的是整篇。拿整篇去查小节产物会放过"从别的节抄来"的条目，
反过来会**冤枉基线**。脚本的 `--scope` 就是干这个的（默认按产物类型自动选）。

> 🩹 **抽样踩过的坑**：第一版直接 `sorted()[:100]`，结果 **100 条全落在字母靠前的 4 个药上**
> （`三氧化二砷`/`乌帕达西替尼`/`他克莫司`/`伤寒疫苗`）——"抽 100 条"变成了"抽 4 个药"。
> 改成**按药轮转**后覆盖 **35 个药**，顺序仍然确定、跑两次同一批。

### 13.3 基线那 6 条不通过的，全都是**改写或拼接**

| 药 | 抽出来的 | 原文 | 性质 |
|---|---|---|---|
| 三氧化二砷 | `孕妇禁用` | `严重的肝、肾功能损害者、孕妇及长期接触砷或有砷中毒者禁用。` | **改写**（缩写了，还补上「禁用」） |
| 三氧化二砷 | `肾功能损害者禁用` | 同上 | **改写**（原文是「严重的肝、肾功能损害者」） |
| 氯氮平 | `低血压患者禁用` | `…低血压、青光眼患者禁用：` | **拼接**（原子是「低血压」，模型补了「患者禁用」） |
| 阿达木单抗 | `对本品或制剂中其它成份过敏者` | `对于本品或制剂中其它成份过敏者（参见【成份】部分）。` | **改字**（删了一个「于」——不是标点差异，所以宽松也查不到） |

最后一条最值得写进论文：**模型比原文更"正确"，但在忠实度上算不通过。**
医疗场景里"忠实于说明书原件"和"写对"是两件事——改写过的句子没法拿回原件核对，
这正是 §13.5 把忠实度定义成查证题的原因。

### 13.4 ⚠️ 修正：§13.2 的 L4 跑通标志**字面无法满足**

### 13.6 一键自检：`scripts/verify_l4.py`

这个项目里数字改过好几次（词表修正、人群词表收敛…），每次都要**手工回去改文档**。
而"**文档里的数和产物里的数不一致**"是最难发现、也最伤诚信的一类错。所以把它变成一条命令：

```bash
python scripts/verify_l4.py                # 全部离线（⑤ 走缓存），不花钱
python scripts/verify_l4.py --with-graph   # 再跑一遍入库与验收查询（需 Neo4j）
```

它做三件事：

1. **重算**——按顺序把 L4 的每个评分步骤**在原进程里**跑一遍。不 shell 出去是有原因的：
   沙箱下外部进程的管道会被拦（`EPERM`），所以直接调各脚本的 `main(argv)`。
2. **断言**——把**已发布的数字写死**在脚本里（`EXPECTED`，16 条），逐个比对。
   数字变了这里就变红。**改文档就必须改 `EXPECTED`，反之亦然**。
3. **核对产物没漂**——重算之后 `git status -- data/extracted` 必须是**干净的**，
   否则说明"提交的产物"和"现在算出来的"不是一回事。

实测输出：

```
✓ 自检全过：9 个步骤 + 16 条数字断言 + 产物零漂移     （--with-graph）
✓ 自检全过：8 个步骤 + 16 条数字断言 + 产物零漂移     （离线）
```

> 写这个脚本时它**当场抓到了我自己的一个错**：基线忠实度那一步**本来就该返回 1**
> （有 6 条原子查不到原文——那正是要被报出来的现象），而我最初把期望退出码写成了 `(0,)`。
> 现在那条的期望值显式写成 `(1,)` 并在名字里注明"预期有 6 条查不到"，
> 免得下一个人以为"基线这一步失败了"。
